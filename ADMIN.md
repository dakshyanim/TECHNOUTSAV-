# Admin dashboard

Apply all migrations in order, including `202610090008_api_limits.sql`. Configure the existing Supabase server-only service-role key. With Node 22.18+ or Node 24, run `npm run setup:admin`, enter a strong password (hidden input), and copy the generated ADMIN_PASSWORD_HASH and ADMIN_SESSION_SECRET into ignored .env.local. Restart the app. Do not prefix either variable with NEXT_PUBLIC_ or paste them into chat. No default admin password exists.

This event dashboard uses one shared organizer account. `/admin/login` verifies a salted scrypt password hash and sets a separate signed, HTTP-only SameSite=Strict admin cookie. Production uses Secure and the __Host- prefix and requires HTTPS. Sessions expire after four hours. Changing the password hash or signing secret invalidates all sessions. Logout records the cookie hash in a private database revocation table before clearing it; copied cookies are rejected on subsequent requests. Revocation checks fail closed when the database is unavailable.

Participant cookies never authorize administration. Every admin page, data reader and API endpoint checks the admin signature/expiry. Mutating endpoints also check Origin, JSON type, bounded body size and server-side field validation. Database admin RPCs and question write grants are restricted to the server service role; anon and authenticated Supabase roles cannot call them. No layout-only or client-side authorization is relied upon.

Origin validation is shared by admin, registration and answer APIs. Production requires an explicitly configured APP_ORIGIN and exact canonical origin match. When APP_ORIGIN is a local loopback URL, development additionally accepts localhost, 127.0.0.1 and IPv6 loopback only when the source protocol/port match the actual local request target. This supports a development instance starting on another port without accepting cross-port requests to the original instance. Missing/null origins, unrelated sites and invalid configuration remain blocked. A trailing slash on the configured root origin is normalized. Run `node scripts/test-request-origin.mjs` for the regression checks. Concurrent local servers can use separate build directories through NEXT_DIST_DIR; the administrator access check uses .next-admin-local to avoid competing with an existing dev server's .next directory.

Login attempts are limited atomically in PostgreSQL to ten per forwarding-address fingerprint and fifty globally per fifteen-minute window, including successful attempts. The global cap prevents forged IP headers bypassing the limit; the host should supply trusted forwarding headers. Limit exhaustion can temporarily block organizer login. The limiter fails closed if the database is unavailable. Raw forwarding addresses are hashed, and stale limiter records are deleted.

The dashboard shows participant/question/submission counts, question management, participants, paginated submissions (50 per page), and current leaderboard standings with a link to the public live display. Question creation includes text, four choices, the correct-choice selector and integer points (0–10,000); activation controls remain on the dashboard; a QR challenge code is generated automatically. Editing preserves IDs and QR codes. Activate/deactivate buttons set status explicitly. Existing attempts and awarded scores remain immutable.

`/api/admin/export` downloads ranked participant results with name, roll number, score, attempts, correct-answer count and registration time. UTF-8 BOM, quoted fields and formula-prefix protection make the CSV suitable for spreadsheet tools. Export and API responses use no-store. Correct answers are only returned to protected question edit pages and are not included in exports or public leaderboard responses.
