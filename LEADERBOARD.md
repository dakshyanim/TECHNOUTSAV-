# Public live leaderboard

Apply migration `202610080006_realtime_leaderboard.sql` after the previous five migrations. Existing participants are backfilled using their last positive-point submission timestamp, falling back to registration time for zero scores. New score timestamps are set by the database after taking the participant row lock. Wrong answers and zero-point answers do not change the timestamp.

Database order is total_score descending, score_reached_at ascending, then UUID ascending. Ranks are unique sequential positions (1, 2, 3), even for equal scores. The indexed order is computed in the read-only `get_leaderboard()` RPC; browsers do not sort or calculate ranks. All registered participants, including zero scores, appear.

Public access is limited to the RPC returning rank, participant UUID, name and score. Raw participant/session/question/submission tables remain private. Public `/api/leaderboard` responses disable caching; `/leaderboard` reads an initial snapshot server-side.

The database trigger sends an empty `changed` broadcast on the public `techno-utsav:leaderboard` topic when participants register, change name/score, or are deleted. Apply migration `202610090009_event_readiness.sql` after all preceding migrations: a private database gate coalesces these notifications to at most one every two seconds across app processes. A nonblocking advisory lock keeps notification contention out of score transactions. There is no delayed trailing event; automatic polling repairs changes suppressed inside the window. The browser subscribes using the publishable key, then refetches the canonical snapshot. No PostgreSQL Changes publication or public SELECT on participants is needed. In Supabase Realtime Settings, allow public channels and enable database Broadcast support; the public flag must match the browser's public channel. The Supabase-managed realtime.send function must exist. Connect the display before scoring so Supabase has initialized its current broadcast partition.

Broadcast payloads never supply scores. Spoofed public messages can only request a throttled refetch, not change rankings. Browser requests cannot overlap, refresh timing includes jitter, and channels/timers are cleaned up on unmount. Automatic fallback polling uses a per-browser interval of 12–18 seconds (15 seconds average), with refetch on reconnect/focus/visibility and an eight-second database read timeout. Identical public reads overlapping within one app process share one in-flight database query; settled results/errors are never cached. Hidden tabs avoid periodic reads and refresh when shown. If the database is unavailable, the screen retains its last successful standings and labels the connection state. A failed notification does not roll back a valid submission; periodic refresh recovers it. Suppressed/missed events can therefore take roughly 19 seconds plus query latency to appear; the connected status alone does not guarantee an instantaneous view.

The page uses a high-contrast large-type table, top-three highlights, tabular score digits and a responsive mobile layout. It requires no registration and no manual refresh. Roll numbers are never displayed.
